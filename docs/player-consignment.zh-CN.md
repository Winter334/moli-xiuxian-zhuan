# 四海商盟玩家寄售

日期：2026-09-29。状态：服务归属、最低价格、成交费率及统一寄售池已确认；
第1批服务端规则、事务存储、回执与API代码已接入，见第9节。
客户端资产预留、交易回执处理和商会临时入口尚未接入，玩家目前还不能从界面办理寄售。
新数据库结构仅编写，未执行建表或改动实际数据。
承接成就履历与璇玑阁开发榜，本稿不把只读榜单或云备份视为已经具备玩家资产交易能力。

## 1. 已确认方向

- 下一项原创功能为玩家交易所，设定为四海商盟提供的寄售服务。
- 玩家在有商会的地方上架物品交易，最低价格不能低于系统回收价。
- 商盟收取成交价的2%。
- 用户最新认可各地商会共用同一寄售池，不按区域拆分玩家市场。
- 各地商会作为当地办理入口，不增加独立交易所地图节点。
- 共用仅针对玩家寄售；各地系统商店保留原有商品、库存、价格及开放条件。
- 查找商品采用分类、品质和价格筛选，不要求玩家逐地查找不同寄售池。

确认与实现仍须区分：以下保留整体方案，当前实际边界以第9节为准。

## 2. 取舍依据

初版面向非盈利Discord社群，玩家与订单数量有限。统一市场有助于将供需集中，
让多余材料、高品质器物与成品丹药更容易找到买家，也不要求买卖双方同时在线。

当前已开放地点可直接前往，没有为商贸运输设计时间、成本或风险。
此时分区更容易增加切换地点查价的步骤，而非形成有意义的运输或经营选择。
四海商盟的世界级商贸网络也适合承接统一寄售业务。

最低价格的目标是避免高阶物品被极低价倾销或近乎白送，但它是财力门槛，
不保证低阶玩家绝对无法购买高阶物品。分区本身同样无法保证：
高阶玩家仍可能返回前期商会出售。
当前不据此自动追加境界、产地或购买资格限制，具体限制须有独立的玩法依据。

以后若地区资源差异、运输或商路成为明确玩法，可重新评估地区市场；
本次共用池是首版取舍，不是永久禁止其它市场组织方式。

## 3. 首版工作默认

以下是首版工作默认，不写成用户逐项指定；服务端已接部分见第9节，客户端流程仍待实现。
实施围绕这一份完整方案推进，普通细节不逐项询问。

| 事项 | 工作默认 |
| --- | --- |
| 交易方式 | 定价寄售；堆叠物按单价和数量上架并可分批购买，有品质的炼材和装备按实例逐件交易 |
| 价格下限 | 复用系统实际回收价；有品质物品按该件实际品质计算，数量与单价对应 |
| 手续费承担 | 买家支付标价，成交后从卖家所得中扣除2%，发布前显示预计到账 |
| 未成交费用 | 不收上架费，撤回未售物品不收费 |
| 挂单管理 | 每角色20个在售位；堆叠物每单最多10000份；首版不自动过期，改价先撤回再重新上架 |
| 物品托管 | 成功上架后物品归商盟保管，不再留在卖家可使用、出售或再次上架的库存中 |
| 领取 | 购买所得、售出货款及撤回物品通过商会领取；卖家离线仍可成交 |
| 商品范围 | 现有普通材料、补给、筑基丹、灵髓、蕴元灵露、炼材和装备可寄售；巡枢残印不寄售，已装备器物先卸下 |
| 成长收益 | 首版玩家交易不额外赠送修为或熟练，不直接照搬系统商店购买的熟练收益 |

最低价按成交价本身判断，不暗中改成“税后所得不得低于系统回收价”。
例如系统回收价100、标价100，按2%成交费卖家所得98；
界面应同时显示回收价与预计到账，让玩家自行比较。
已买到的物品仍沿用其原有使用条件。例如买到筑基丹不等于能够提前服用，
也不改变境界、根基和神通的取得规则。

20个在售位用于约束挂单量，不增设付费扩容；10000份沿用当前原型单次批量操作量级。
不自动过期是为了减少初期社群反复续挂的维护成本，不是永久否定以后按实际订单量调整。
这些是初版容量默认，不据此重调物品产量、系统商店价格或玩家成长。

## 4. 上架到领取的完整流程

### 上架

在当前已开放商会选择行囊物品，填写数量、单价；器物显示实际品质与属性。
发布前显示系统回收价、标价、全数成交预计手续费及净所得。
服务端依据本次核对的角色状态检查商会资格、归属、数量、装备状态和价格下限。
成功后从可用库存移出物品并建立托管订单；上架不收钱，不改变炼制或采集履历。

### 购买

堆叠物可输入所需数量，器物逐件购买，不允许购买自己的挂单。
确认页面展示实际总价；购买请求带明示的订单、单价和数量。
若余量不足或订单已撤回，整笔拒绝并刷新，不自动减少购买量、换一个卖家或提高价格。
多个买家争购时，由服务端保证实际成交数量不超过托管余量。

成交一次完成：扣买家灵石、减少订单余量、登记买家的待领物品、
登记卖家税后待领货款及手续费。上述任一步失败则整笔不成交。
买家取物不再付钱，卖家取款不再次扣手续费。
卖家离线不影响别人购买，但成交不会直接修改卖家的角色快照。

### 撤回

可撤回未售余量，包括部分成交后的余量，不退回已经成交的部分或其手续费。
撤回后未售物品进入自己的待领取，立即释放在售位。
撤回与购买并发时以实际成交先后为准，已售部分留在成交账中，
尚未售出的部分只返还一次。全数售出同样释放在售位。

### 领取

可在任一已开放商会领取自己的购买所得、撤回物品和货款，不要求返回原上架地点。
待领资产保存在商会服务端，不设保管费和过期删除；它们不是行囊物品或当前灵石余额，
不能直接使用、再次寄售或计入灵石榜。

领取按明确的待领条目和数量办理，受现有行囊容量、堆叠数量及余额上限约束；
可分批领取，暂时放不下的余量继续保留，不吞物品、不强制截断余额。
器物保留物品种类与品质，入袋时分配领取者自己的实例编号，
不把卖家的 `item-编号` 直接放入买家行囊。

## 5. 手续费口径

灵石仍用整数。首版采用**同一寄售单累计成交额的2%向上取整**，
每次成交只扣累计手续费新增的部分：

```text
累计手续费 = ceil(累计成交额 / 50)
本次手续费 = 本次成交后累计手续费 - 本次成交前累计手续费
本次卖家所得 = 本次成交额 - 本次手续费
```

例如同一单先成交30灵石，再成交20灵石：
第一次手续费1，第二次新增手续费0，累计成交50、手续费1、净得49。
这与一次买走50灵石商品相同，不因买家把一张订单拆成小份购买而多扣卖家的手续费。
单张订单全部成交后的取整误差小于1灵石；金额很小的首次成交可能没有净到账，
发布和成交记录要显示实际整数费用，不声称每笔小额成交都恰好只扣2%。

未售部分不计税，部分成交后撤回也不加收剩余部分的手续费。
撤回后重新挂单属于新订单，重新计算；不会因拆单或反复撤挂减少已发生的手续费。
这里只新增寄售费计算，不改系统商店原有回收取整函数。

- 现有 `core/prototype/economy.ts` 的买卖只移动角色与系统商店库存，买入还会增加熟练。

- `shared/client-save.ts` 已有进度与容量检查，`server/client/service.ts` 已有上传幂等、
  版本冲突与限流，但没有跨玩家托管或成交账。
- `src/local-save.ts` 已持久化待上传请求，`src/game-client.ts` 有串行本地动作和低频备份；
  都尚不支持交易资产预留、交易回执或交易结果核对。

### 在线交易检查点

工作方案保留客户端战斗与成长，只把寄售资产变更交由服务端确认：

1. 发起交易前先处理已有云上传回执，确保身份与云存档版本一致；
   本次交易携带最新本地进度和预留前的角色快照，服务端沿用基础保存校验。
   不把60秒备份周期或普通上传10秒间隔直接变成玩家的交易冷却。
2. 客户端先把固定请求编号、请求内容和预留资产写入本地存档，再发送。
   上架物品或购买款从可用资产中预留，不能同时使用、卖给系统或再次寄售；
   领取则预留必要的入袋空间或余额额度，未确认的收入不能提前使用。
3. 服务端在同一数据库事务内核对角色版本、订单和待领资产，
   完成扣款/托管/交付登记，保存结果回执并推进本次角色的保存与交易版本。
   商品托管使用全局交易标识，角色自己的实例编号只在角色内部使用。
4. 客户端收到确定结果后，按原请求结清预留并只应用一次确认的资产及记录变更。
   若期间角色继续游玩，不用交易开始时的整份快照覆盖当前角色；
   回执处理、版本更新与清除待处理请求应当一起落盘。
5. 普通云备份还须核对最后确认的交易版本，旧检查点不能跨过已经发生的交易覆盖资产。
   同一角色同时只保留一笔未确认交易；自动云上传待其核对完毕后恢复，
   避免普通备份与交易请求互相覆盖。

请求超时或断线不代表没有成交，不直接退回预留，也不换新编号重做。
重连或重开后先用原编号查回执；只有明确成功或服务端已终结的失败才能结清该请求。
“查无记录”也不能当作失败，原请求可能还在处理。
重复提交必须得到同一终局结果，相同编号换内容须拒绝。

这期间只冻结相关资产、所需接收额度及新的交易/云上传，
其余本地活动与本地保存继续，不因云服务断线整体停玩；
容量检查须把尚未结清的预留一并考虑，避免继续游玩后无处接收已成交物品。
真正出现身份或多端存档冲突时保留现有数据，明确报错，不自动覆盖、回档或重置角色。

卖家离线收到货款时，只更新订单与商会待领资产，不递增其角色的交易版本或云快照版本。
以后主动领取时再经过上述检查点，因此普通低频备份不会擦掉离线成交货款。
此处离线成交不是离线战斗收益，不改变原有关闭/挂起后停止战斗结算的规则。

以上保证正常重试、并发、乱序和旧检查点不会造成重复转移，
不证明客户端历史资源来源绝对真实，不恢复服务端重放战斗或承诺竞技级反作弊。

## 7. 信息与记录

商会内用“寄售货单、我的寄售、待领取”三个视图承接，不建独立地图节点。
公开货单只显示商品、品质/属性、单价、余量和卖家显示名，
不公布卖家的位置、未开放区域或完整行囊。支持名称、类别、品质和价格筛选，
分页显示；具体排版留到临时入口接入及后续正式UI阶段。

寄售购入支出、售出毛额、手续费和净所得从服务端成交账独立累计；
领取只转移已登记资产，不再次记成一笔买卖。现有系统商店履历不改含义，
买到的装备不记成自制，买到的材料不记成采矿所得。
灵石榜仍是角色当前余额，待领货款不计入；领取后随成功保存反映，不另改为总资产榜。

当前只有开发身份，先做隔离开发市场与必要的试修显示名。
正式公开交易需要稳定账号身份和对应环境隔离，不能仅靠测试标记冒充正式交易资格。

单价工作上限为现有余额上限 `10^12` 灵石，避免单件定价超出当前角色支付能力；
一单总价仍可高于余额上限，买家按实际支付能力分批买，精确整数运算不转浮点数。
未因此修改系统商店回收价、库存、制作收益或容量规则。

### 事务与保存

新增独立模块：

- `core/prototype/consignment.ts`：商会资格、资产选择、下限、手续费及纯资产变更。
- `shared/consignment.ts`：请求、终局回执、货单、待领和分页契约。
- `server/client/consignment.ts`：上架、购买、撤回、领取及读取服务。
- `server/client/consignment-store.ts`：PostgreSQL事务、托管与待领存储、成交账、持久回执。

发起者角色用非键更新行锁串行处理保存与交易，再锁定目标货单或待领条目；
避免同时争购超卖，也避免普通备份在交易中间覆盖角色。
非键锁允许卖家角色的外键检查通过，避免卖家撤回等待订单、买家又等待卖家角色的互锁。
业务检查和资产变更先在副本上完成，容量及角色校验通过后才写库；
角色、订单、待领、成交账和成功回执在同一事务提交，存储失败整笔回滚。

交易使用固定请求编号和完整请求内容摘要，成功与明确业务拒绝都保存终局回执；
重发返回原结果，同编号改内容拒绝。回执独立保存，不被后续普通上传或新交易替换。
查无回执返回 `unknown`，不是失败或退款许可；临时存储异常不伪造终局失败。
身份/格式在进入交易前不合法的请求仍由API拒绝，不变成已受理交易。

云封装升至 `opening-client-2`，新增必填 `tradeRevision`，新角色从0开始。
每次成功的主动寄售操作同时推进云保存版本与交易版本，普通备份只可携带当前交易版本；
不允许旧检查点跨过已确认交易，也不允许普通备份自行增加交易版本。
交易不套用普通上传的10秒间隔，不把60–75秒备份周期当作交易冷却。
本地封装仍为 `opening-local-2`，角色5、内核4、内容2未改，但嵌套旧云封装的本地存档同样拒读。
没有旧数据补全、迁移、清库、重置或自动覆盖。

`server/client/001_initial.sql` 为新结构增加货单、待领、成交账和回执四张表及必要索引。
现有初始化器按建表脚本校验和拒绝旧数据库结构，不自动给已有库追加表或升级记录。
本批只改脚本，没有执行任何数据库操作；旧库不能直接用新代码启动，保留原数据待明确处置。

API已注册在当前开发身份服务下：

| 接口 | 行为 |
| --- | --- |
| `POST /api/client/consignment/view` | 携带最新检查点及当地商会、页码和筛选，仅校验读取，不上传进度或推进版本 |
| `POST /api/client/consignment/command` | 携带预留前快照、当前云版本、固定请求号和明确操作；返回成功或已记录的拒绝回执 |
| `GET /api/client/consignment/receipts/:requestId` | 仅查询当前身份自己的回执；离开商会仍可核对，不因此再次转移资产 |

成功回执只提供资产变更及新版本，不要求客户端用交易开始时的整份快照覆盖后续进度。
当前客户端仍未实现预留/核对流程，不能直接把普通本地动作当交易命令发送；
下一批须将资产预留、容量预留、回执应用与版本更新一起落盘，再提供玩家入口。
领取器物时按最新本地编号分配；预留期间的其它活动不应被旧快照覆盖。

### 本地预留与确认

- 新增 `src/trade-reservation.ts`，根据固定请求导出唯一预期资产差额。
  上架预留所选堆叠物/器物，购买预留精确总款，领取预留对应堆叠上限、余额额度或器物位置。
- 预留出资仍保存在持久库存内，但从所有本地操作和界面的可用角色快照扣除，
  不能用于装备、服用、制作、系统售出或再寄售。每次本地动作后还原托管部分再落盘，
  因此拒绝时只解除预留，器物原编号、品质及等待期间新挣得的物资都保留。
- 容量检查包括个人商店里的器物及待领额度，不让新制作、购入、发放或活动收益抢占空间。
  手动动作超容量整笔不提交；交易等待期间活动按事件检查，若某事件收益无法容纳，
  保留上一个检查点并暂停该段活动计时，不先给奖励再丢弃，也不阻止腾空间、移动等本地操作。
- 固定请求、预期差额及请求时本地版本在发网前一起写盘。写入失败不发送；
  回执写入失败保留原预留，下次仍可核对。网络请求不占用本地动作串行队列。
- 先收妥已有普通上传的回执，再建立交易检查点；不为交易强制发起一次普通上传，
  不套用普通上传间隔。只有一笔未确认交易，新交易与普通云上传待其确认后继续。
- 新提交直接发送已持久化请求；超时不退款。重开、手动核对和低频定时核对先查询原编号，
  `unknown` 只允许原样重发，不能取消预留或另起编号。离开商会也能核对原交易。
- 成功回执核对身份、请求号、云版本/交易版本、资产差额及目标订单/待领编号，
  对最新本地角色应用一次差额，不用旧快照覆盖等待期间的位置、成长、装备或活动进度。
  领取器物按最新 `nextInstanceId` 分配，不与期间炼制/发放的器物冲突。
- 明确业务拒绝解除预留；身份、保存/交易版本冲突或回执内容不匹配会停止云上传和新交易，
  冲突原因持久保存，不通过重开绕过。未确认结果保留请求和预留，不自动退款、回档或覆盖。
  已确认的冲突拒绝可解除其预留，但停止在线资产操作的状态与解除预留一起落盘。
- 成功资产、交易版本、云版本及清除请求原子落到同一份本地存档；
  停止后的迟到网络响应不更新新会话。已有云上传与校时也补上对应的会话/请求保护。
